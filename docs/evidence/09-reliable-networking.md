# Evidence for chapter 09: Reliable requests on unreliable networks

What Phase 27 checked the chapter’s claims against, and where the outline was wrong. [PLAN.md](../PLAN.md), under “Decisions: evidence”, says what counts as evidence. Phase 27 was written in a cloud container, without Codex, the Unity Editor, the probe project, Xcode or a device, so that session gathered the evidence itself under rule A of the brief, on 2026-09-25. The container could not reach docs.unity3d.com, rfc-editor.org, datatracker.ietf.org, learn.microsoft.com, w3.org or owasp.org. Unity's C# reference source at the tag `6000.3.11f1` stood in for the Editor's assemblies, and the documents' own repositories on GitHub stood in for the RFC Editor, the IETF and OWASP; each is pinned to a commit in the receipts. The Mac's session merged the chapter after chapters 07 and 08 on 2026-09-26, checked what the container could not, and aligned the chapter with those two chapters; “Checked on the Mac” says what that changed.

## Checked, and against what

### network-timeouts

- `UnityWebRequest.timeout` is an `int` in whole seconds, stored as milliseconds, and a sent request refuses a new value (`UnityWebRequest has already been sent; cannot modify the timeout`): confirmed. [UnityWebRequest.bindings.cs](https://raw.githubusercontent.com/Unity-Technologies/UnityCsReference/6000.3.11f1/Modules/UnityWebRequest/Public/UnityWebRequest.bindings.cs), lines 621 to 633. The 6000.3 reference: “The number of seconds after which UnityWebRequest attempts to abort the request if no response is received.”
- `UnityWebRequest` has one timeout and no separate connection timeout: confirmed for the C# API; the same file has no other timeout member.
- What that timeout bounds differs by platform, so the chapter does not use it as the attempt's limit: chapter 8's evidence found that the Editor applied it to the whole transfer, and the iOS Trampoline sets `request.timeoutInterval = timeoutSec` (`PlaybackEngines/iOSSupport/Trampoline/Classes/Unity/UnityWebRequest.mm`, line 441), which [Apple defines](https://developer.apple.com/documentation/foundation/nsurlrequest/timeoutinterval) as idle time: “If during a connection attempt the request remains idle for longer than the timeout interval, the request is considered to have timed out.” The chapter times each attempt with its own `CancellationTokenSource` and leaves `timeout` to chapter 8's transport as a guard against a stall. The attempt takes the layer below as a `SendAsync` delegate, since chapter 8's `SessionClient` has the transport's method shape without implementing `IHttpTransport` (`08-backend-clients.md`, line 435); the harness converts both methods to the delegate. `SessionClient` awaits its shared refresh without the caller's token and sends it with `CancellationToken.None` (lines 460, 469 and 502), so the chapter says that a refresh is limited by the transport's stall guard and not by the attempt's timer.
- Chapter 8's transport aborts its request when the token it is given is cancelled, and the `await` throws `OperationCanceledException`: chapter 8's evidence, run 2. `CancelAfter` cancels from a timer on a pool thread; in the Mac's run 2 below, the transport still resumed on the main thread after the timer aborted its request, and in runs 1 to 3 Unity logged no error. `Abort` is `[NativeMethod(IsThreadSafe = true)]` (`UnityWebRequest.bindings.cs`, line 295), and `Awaitable.Cancel` calls into native code for a native awaitable ([Awaitable.cs](https://raw.githubusercontent.com/Unity-Technologies/UnityCsReference/6000.3.11f1/Runtime/Export/Scripting/Awaitable.cs), line 244).
- `MonoBehaviour.destroyCancellationToken` exists and is cancelled from native code when the object is destroyed: confirmed. [MonoBehaviour.bindings.cs](https://raw.githubusercontent.com/Unity-Technologies/UnityCsReference/6000.3.11f1/Runtime/Export/Scripting/MonoBehaviour.bindings.cs), lines 29 to 48.
- `HttpClient.Timeout` defaults to 100 seconds and applies to each call on the instance; a caller's token also applies, and the shorter wins: confirmed by the [API docs source](https://github.com/dotnet/dotnet-api-docs/blob/main/xml/System.Net.Http/HttpClient.xml), lines 3498 to 3504, and by the .NET 8 probe below.
- A timeout and a caller's cancellation throw the same type, `TaskCanceledException`, an `OperationCanceledException`, and the caller's token tells them apart: confirmed by the .NET 8 probe, and for Unity's Mono by chapter 8's evidence, run 1.
- Cancellation stops the client's waiting and does not tell the server to stop: the .NET 8 probe's server finished both requests that the client had abandoned, one by timeout and one by its token, and in the Mac's Unity runs the local server completed every slow request after the client had stopped waiting. A backend may also stop work when the client goes, so the chapter says that the server's work may run to its end or may already have committed, which leaves a cancelled write's outcome unknown.
- A per-attempt timeout does not bound an operation that retries, and a deadline does: confirmed by the .NET 8 probe, with 3.0 s for three attempts of 1 s each, and 1.5 s and two attempts under a 1.5 s deadline. The chapter's own attempt code clipped a 10-second limit to a deadline 1.5 s away, ending at 1.50 s, in run 3.
- A gateway that gives up on its upstream answers 504: confirmed, RFC 9110, section 15.6.5, read in the HTTP working group's copy of the RFC.
- iOS gives `applicationDidEnterBackground(_:)` five seconds and then suspends the app: confirmed, Apple, [Extending your app’s background execution time](https://developer.apple.com/documentation/uikit/extending-your-app-s-background-execution-time). While the app is suspended the system may reclaim its sockets and close their connections: confirmed, Apple's archived [TN2277](https://developer.apple.com/library/archive/technotes/tn2277/_index.html).
- Background transfers: a background `URLSession` configuration lets transfers continue while the app is suspended or terminated ([Apple](https://developer.apple.com/documentation/foundation/urlsessionconfiguration/background(withidentifier:))); Android has `DownloadManager` for long-running HTTP downloads ([reference](https://developer.android.com/reference/android/app/DownloadManager)) and user-initiated data transfer jobs ([data transfer options](https://developer.android.com/develop/background-work/background-tasks/data-transfer-options)): confirmed, and named only.

### network-retries

- PUT, DELETE and the safe methods are idempotent, and a client should not retry a non-idempotent request unless it knows the request is idempotent or was never applied: confirmed, RFC 9110, section 9.2.2. Chapter 8 states the same rule, and the chapter now points to it.
- 408 lets the client repeat the request; 502 and 504 come from a gateway that had forwarded the request; 503 means the server is unable to handle the request for now; `Retry-After` holds seconds or an HTTP date: confirmed, RFC 9110, sections 15.5.9, 15.6.3, 15.6.4, 15.6.5 and 10.2.3. 429 and its optional `Retry-After`: RFC 6585, section 4.
- 500, 502, 503 and 504 are retried only for an idempotent or keyed request, as chapter 8's status table does (“Retries later, if the request is harmless to repeat”, and for 502 to 504 “with the same caution”). The draft had retried a 503 for any method and left out 500.
- 401 means the request was not applied for lack of valid credentials; 403 that the server understood and refuses; 409 a conflict with the resource's state; 422 content the server could not process: confirmed, RFC 9110, section 15.5. The 401 handling, one refresh shared by concurrent requests and one resend, with a second 401 as the answer, is chapter 8's session layer.
- A failure without an HTTP answer: chapter 8's evidence shows that `UnityWebRequest` ends a refused connection, an unknown host, a timeout and an abort alike with `ConnectionError`, which its transport returns with status 0. The Mac's run 1 read the `error` texts in the Editor: “Cannot resolve destination host” and “Cannot connect to destination host”.
- An SDK sits behind an adapter of the game's, and a proxy on the device's traffic shows the requests it sends: chapter 7, sections `sdk-analytics-integration` and `sdk-evaluation`.
- The recap of backoff with full jitter, a cap and a deadline: the first book's chapter 13, `content/unity-engineering/13-liveops-and-releases.md`, lines 257 to 282.
- Retry budgets exist in practice: gRPC's client retry design disables retries when a client's ratio of failures to successes passes a threshold ([proposal A6](https://github.com/grpc/proposal/blob/master/A6-client-retries.md)). The chapter describes a budget without naming a library.
- A 409 is retried only when the caller marks it as the error the backend documents for a key whose first request still runs, since an endpoint that takes keys can still answer 409 for a conflict with the resource's state (chapter 8's status table); the draft's example gives that error the title “A request is outstanding for this Idempotency-Key”. The policy table's decisions, one status at a time, were printed by the chapter's own `ShouldRetry` in runs 3 and 4 and match the section's table.

### network-idempotency

- The `Idempotency-Key` header is an Internet-Draft of the IETF HTTPAPI working group, not a standard: the [datatracker](https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header/), read on 2026-09-26, lists versions 00 to 07, the latest revision on 2025-10-15, the document as an “Expired Internet-Draft”, and no RFC. The working group's [repository](https://github.com/ietf-wg-httpapi/idempotency) had shown only version 06.
- The draft's rules, all confirmed in the repository's copy of version 06 at commit `dab060c`: the key is unique and never reused with a different payload; a UUID or similar random identifier is recommended; the value is a Structured Field String, so it travels in double quotes; the server may expire keys and should publish the policy; a retry after completion gets the recorded result, success or error; a retry while the original is in flight gets 409; a key reused with another payload gets 422; a missing required key gets 400; after a 409 the client retries without changing the request. Version 07, from the IETF archive, states each of these in the same words; a paragraph diff of 06 and 07 finds only the dates, the table of contents and the change log.
- The first book's rule that the pending record is saved before the request is sent: `content/unity-engineering/03-missions-and-rewards.md`, lines 157 to 175.
- The lost-response case: the probe's raw socket server committed each write and closed the first connection without answering. With the same key, the retry returned the recorded result and the server applied one write; with a new key for the retry, it applied a second.
- The chapter's `ToRequest` sent the same key, quoted, and the same body on two attempts through chapter 8's transport, as the local server logged in run 3.

### network-offline

- `Application.internetReachability` returns “the type of Internet reachability currently possible on the device”, and `NetworkReachability` has `NotReachable`, `ReachableViaCarrierDataNetwork` and `ReachableViaLocalAreaNetwork`: confirmed from the source comments, [Application.bindings.cs](https://raw.githubusercontent.com/Unity-Technologies/UnityCsReference/6000.3.11f1/Runtime/Export/Application/Application.bindings.cs), line 453, and `Application.cs`, lines 42 to 51, and from the Editor's `UnityEngine.CoreModule.xml`, lines 520 to 524 and 28952 to 28971. The [6000.3 reference page](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/Application-internetReachability.html) adds: “This property is mostly useful on handhelds to distinguish fast and cheap WiFi connection from carrier networking.” and “Note: Do not use this property to determine the actual connectivity. For example, the device can be connected to a hot spot, but not have the actual route to the network.”
- Android separates a network set up for the internet from one where the system found actual access: `NET_CAPABILITY_INTERNET` “is about setup and not actual ability to reach public servers”, `NET_CAPABILITY_VALIDATED` “indicates that the network provides actual access to the public internet when it is probed”, a network behind a captive portal lacks it, and after the user logs in to the portal “the network gains the NET_CAPABILITY_VALIDATED capability and loses the NET_CAPABILITY_CAPTIVE_PORTAL capability”: confirmed, Android, [Read network state](https://developer.android.com/develop/connectivity/network-ops/reading-network-state).
- On iOS, a satisfied `NWPath` is one “available to establish connections and send data”: confirmed, [Apple](https://developer.apple.com/documentation/network/nwpath/status-swift.enum/satisfied).
- Captive portals forge DNS or HTTP responses, and some intercept HTTPS; an intercepted TLS connection gives a host name mismatch; and portals work as intended only with browsers, breaking other applications: confirmed, the capport architecture draft 10, which became RFC 8952, in the working group's [repository](https://github.com/capport-wg/architecture).
- Plain HTTP: “Allow downloads over HTTP” defaults to `NotAllowed`, under which `UnityWebRequest` refuses plain HTTP except to `127.0.0.1` and `localhost`, and `HttpClient` is not subject to it: chapter 8's evidence, run 2; the setting's values: chapter 6, `xcode-build-settings`.
- `If-Match` guards a state-changing request against a lost update, and a failed condition answers 412: confirmed, RFC 9110, sections 13.1.1 and 15.5.13. Chapter 8 teaches the conditional write with the same cloud-save case, and the chapter now points to it.
- The bounded offline queue and the pending, confirmed and rejected states: the first book, chapter 13, line 263, and chapter 3, lines 171 to 175.

### network-observability

- W3C Trace Context's `traceparent` header identifies a request in a tracing system: confirmed in the specification's [repository](https://github.com/w3c/trace-context), `spec/20-http_request_header_format.md`.
- Session identifiers, access tokens and sensitive personal data should be removed, masked, sanitized, hashed or encrypted rather than logged: confirmed, OWASP's Logging Cheat Sheet in its [repository](https://github.com/OWASP/CheatSheetSeries).
- On Android, logs are a shared resource available to apps with `READ_LOGS`, and Android advises limiting logs in production: confirmed, Android, [Security tips](https://developer.android.com/privacy-and-security/security-tips).

## Rests on documentation alone

- The HTTP semantics rest on RFC 9110 and RFC 6585, and the key's behavior on the draft. Servers differ: the draft says what a server SHOULD do, and the chapter sends the reader to the backend's own documentation for its rules and retention window.
- iOS suspension, socket reclaim and background sessions rest on Apple's pages; TN2277 is an archived note from iOS 4. No device was run.
- Android's capabilities, `DownloadManager` and user-initiated jobs rest on Android's pages.
- The attempt timer was run only in the Editor. That it resumes on the main thread on a device, under IL2CPP, rests on the timer reaching the same native `Awaitable` cancellation.
- Choosing timeouts from latency percentiles, the order of timeouts from server to deadline, retry amplification, budgets, circuit breakers, correlation ids and the per-feature offline strategies are design reasoning that the chapter shows, not facts about a platform. The amplification figures are arithmetic.

## Narrowed or cut

- “Its requests fail on resume” became: a suspended app runs no code, and the system may reclaim its sockets, so a request in flight can fail when the app resumes, with an unknown outcome.
- The chapter does not state what a `UnityWebRequest` does with a captive portal's redirect, nor what `internetReachability` reads on a portal's network: on Android that depends on whether Unity's player checks `NET_CAPABILITY_VALIDATED`, which is native code. The reachability questions rest on the property's definition and the reference's note.
- A 502 can come from a gateway that never reached its upstream, so the chapter says a gateway “may have forwarded” the request.
- W3C Trace Context is called a specification, since its status page on w3.org could not be read in the container.
- A background `URLSession` keeps transfers going after the system terminates the app, and Apple's page adds that a user's force quit cancels them, so the chapter says “after the system terminates it”.
- The checks of status, `Content-Type` and schema are described as rejecting what the endpoint would not send, such as a portal's page, and not as proof of who answered, which only HTTPS with a validated certificate gives. The captive-portal question now says that the portal intercepts the connection; a portal that blocks HTTPS leaves the request to time out, as the prose says.
- The draft's `TimeoutException` nested inside an `HttpClient` timeout on .NET 8 was cut from the chapter: the owner's token is the test, as in chapter 8, and whether Unity's class libraries nest it was not checked.

## Where the outline fell short

- **Retry amplification.** Three layers that “each retry three times” make four attempts each, 4 × 4 × 4 = 64 at the bottom; 27 is the figure for three attempts each. The chapter counts attempts and gives both.
- **The captive portal's 200.** A portal can answer a cleartext request with its own page. An HTTPS request cannot be answered in the server's name: interception gives a host name mismatch, so the game sees a TLS failure, a connection error. The chapter teaches both cases and keeps the check of content type and schema for anything that answers in the server's place.
- **The list of retryable failures.** 502 and 504 come from a gateway that had already forwarded the request, and a connection can drop after the request was sent, so for a POST without a key they are unknown outcomes, like a timeout. The chapter retries them only for idempotent or keyed requests, and retries a connection error for any method only when it happened before the request was sent.
- **The header's syntax.** The draft makes the key a Structured Field String, so the header carries it in double quotes. The outline did not say so.
- **Timeouts at each layer.** `UnityWebRequest` has no connection timeout of its own, and its one timeout bounds the whole transfer in the Editor and idle time on iOS, so the game times the attempt itself.

## Checked on the Mac

On 2026-09-26, against the sources named:

- **Unity's reference, 6000.3.** The pages for `Application.internetReachability`, `UnityWebRequest.timeout` and `UnityWebRequest.Abort` returned 200, and their wording matches the Editor's XML doc comments. They support the chapter's two claims: reachability names the kind of route and says nothing about the server, and a request has one timeout, in whole seconds, set before it is sent. Chapter 8's finding on what that timeout bounds changed the chapter: its attempt code no longer sets `timeout` to the time left, and times each attempt with a linked `CancellationTokenSource` through chapter 8's transport.
- **The C# samples** compile against 6000.3's assemblies for both platforms, and run 3 ran them. Two of them changed to build on chapter 8's types: the attempt takes the `SendAsync` of chapter 8's session layer or transport and an `ApiRequest`, and returns an `ApiResponse`, and `Operations.ToRequest` builds an `ApiRequest` in place of a `UnityWebRequest`, so the session layer adds the token. `ShouldRetry` takes the `int` status of `ApiResponse`, retries 500 and 503 only for idempotent requests, and retries a 409 only when it is the backend's error for a key whose first request still runs, as the idempotency section's table says.
- **The draft's status**: version 07 exists and has expired, with no RFC. The sentence in `network-idempotency` now says so; no question depends on it.
- **The links**: `https://www.rfc-editor.org/rfc/rfc9110.html#name-idempotent-methods`, the datatracker page and OWASP's cheat sheet each return 200 with no redirect.
- **The receipts**: `check_receipts.py` re-fetched 73 receipts; the 13 that point at the container's scratchpad failed with “no file” or “no log”, as expected, and the other 60 passed.
