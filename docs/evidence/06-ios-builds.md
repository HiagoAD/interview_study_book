What Phase 24 checked the chapter’s claims against, and where the outline was wrong. [PLAN.md](../PLAN.md), under “Decisions: evidence”, says what counts as evidence. Documentation was read on 2026-09-25. The reference Editor is Unity 6000.3.11f1. Export paths below are relative to the probe project.

## Checked, and against what

### xcode-build-flow

- Replace overwrites the old Xcode project; Append preserves some edits while overwriting selected values: confirmed. Unity [How Unity builds iOS applications](https://docs.unity3d.com/6000.3/Documentation/Manual/how-unity-builds-ios-applications.html). The same page describes Append as regenerating the project root, `Data` and `Libraries`, updating the project file, and keeping suitable custom code under `Classes`; Append requires an export from the same Unity iOS version.
- The Append API is `BuildOptions.AcceptExternalModificationsToPlayer`: confirmed. Unity [Scripting API](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/BuildOptions.AcceptExternalModificationsToPlayer.html) and `Unity.app/Contents/Resources/Scripting/Managed/UnityEngine/UnityEditor.CoreModule.xml:9172` relative to `6000.3.11f1/`.
- Unity generates C++ from C#, and Xcode invokes IL2CPP to compile it: confirmed. Unity [build process](https://docs.unity3d.com/6000.3/Documentation/Manual/how-unity-builds-ios-applications.html). In this export, `GameAssembly` has a shell phase that runs IL2CPP with `--compile-cpp` and produces `libGameAssembly.a`: `Exports/iOS/Unity-iPhone.xcodeproj/project.pbxproj:1055` and `:1180`. Describe this as an IL2CPP build driver invoked by Xcode, rather than Xcode compiling all generated `.cpp` files as ordinary Sources entries.
- The export's main target has `Debug`, `ReleaseForRunning`, `ReleaseForProfiling`, and `Release`; the shared scheme's Archive action uses `Release`: confirmed. `Exports/iOS/Unity-iPhone.xcodeproj/project.pbxproj:2296` and `Exports/iOS/Unity-iPhone.xcodeproj/xcshareddata/xcschemes/Unity-iPhone.xcscheme:41`.
- The archive configuration requests `dwarf-with-dsym`: confirmed for `GameAssembly` in `Exports/iOS/Unity-iPhone.xcodeproj/project.pbxproj:1765`. The other target settings should be read independently rather than assumed identical. Apple says an archive includes the app's binaries and dSYMs: [debugging information](https://developer.apple.com/documentation/xcode/building-your-app-to-include-debugging-information) and [distribution flow](https://developer.apple.com/documentation/xcode/distributing-your-app-for-beta-testing-and-releases). Keep the archive as the reproducible symbol-bearing build artifact.
- `xcodebuild -exportArchive` uses `-archivePath`, `-exportPath`, and `-exportOptionsPlist`: confirmed by Xcode 27.0 `xcodebuild -help` in the run receipts. Its current iOS method names are `app-store-connect`, `release-testing`, `enterprise`, `debugging`, and `validation`. It still lists `app-store`, `ad-hoc`, and `development` as deprecated aliases. `destination` chooses `export` or `upload`; `signingStyle` chooses `automatic` or `manual`; `manageAppVersionAndBuildNumber` defaults to yes for upload; `uploadSymbols` defaults to yes for App Store exports. The help also lists macOS methods, so do not present the full method list as all applicable to an iOS archive.
- Xcode's archive is not the exported IPA: confirmed in Apple [distribution flow](https://developer.apple.com/documentation/xcode/distributing-your-app-for-beta-testing-and-releases), which says Xcode repackages the archive according to the distribution configuration. The exact IPA contents and whether this particular export would place symbol files in the package remain unverified because this archive could not be exported. Apple [debugging information](https://developer.apple.com/documentation/xcode/building-your-app-to-include-debugging-information) supports keeping dSYMs in the archive and optionally uploading them separately.
- Current upload routes include Xcode, Transporter and `altool`: confirmed by Apple [Upload builds](https://developer.apple.com/help/app-store-connect/manage-builds/upload-builds). Apple also documents a [build uploads API resource](https://developer.apple.com/documentation/appstoreconnectapi/build-uploads); older API prose on a different Apple page says binaries cannot be uploaded directly through the API, so the writer should use the current resource and avoid claiming either universal support or deprecation without a dated Apple notice.
- A local complete iOS build needs macOS because Xcode runs there: confirmed by Unity [Build an iOS application](https://docs.unity3d.com/6000.3/Documentation/Manual/iphone-BuildProcess.html). Unity 6000.3 lists iOS 15 or later and Xcode 16 or later: [system requirements](https://docs.unity3d.com/6000.3/Documentation/Manual/system-requirements.html). App Store Connect has its own changing upload requirements: Apple [Upload builds](https://developer.apple.com/help/app-store-connect/manage-builds/upload-builds).

### xcode-signing-model

- A signing identity consists of the certificate and its matching private key; a certificate alone cannot sign: confirmed by Apple [TN3161](https://developer.apple.com/documentation/technotes/tn3161-inside-code-signing-certificates). Apple's [certificates overview](https://developer.apple.com/help/account/certificates/certificates-overview) names Apple Development and Apple Distribution and their uses. Local keychain identities and cloud-managed distribution certificates are distinct workflows; do not imply every signing key must be exported as a local file.
- An App ID identifies an app in a provisioning profile, can be explicit or wildcard, and has an allowlist of capabilities: confirmed by Apple [Register an App ID](https://developer.apple.com/help/account/identifiers/register-an-app-id). Apple's [TN3125](https://developer.apple.com/documentation/technotes/tn3125-inside-code-signing-provisioning-profiles) describes the prefix plus bundle identifier and a profile binding signer certificates, app identity, devices or distribution scope, expiry and entitlement allowance.
- Development and ad hoc provisioning use registered devices; App Store profiles do not list devices; enterprise profiles cover all devices: confirmed by [TN3125](https://developer.apple.com/documentation/technotes/tn3125-inside-code-signing-provisioning-profiles), Apple's [ad hoc profile guide](https://developer.apple.com/help/account/provisioning-profiles/create-an-ad-hoc-provisioning-profile), and [device registration updates](https://developer.apple.com/help/account/reference/device-registration-updates). An App Store-distributed app is re-signed by Apple, so its final installation does not carry the original App Store provisioning profile, per TN3125.
- The profile's entitlements are an allowlist, while the app claims entitlements in its code signature: confirmed by [TN3125](https://developer.apple.com/documentation/technotes/tn3125-inside-code-signing-provisioning-profiles). Xcode combines the entitlements file, account and project information while signing: Apple [Entitlements](https://developer.apple.com/documentation/bundleresources/entitlements). A claim outside the profile's allowance must be removed or the App ID and profile updated. Changes to App ID capabilities can invalidate existing profiles: Apple [Enable app capabilities](https://developer.apple.com/help/account/identifiers/enable-app-capabilities).
- Automatic signing lets Xcode manage signing assets; manual signing uses chosen team, certificate and profile: confirmed by Apple [registered-device distribution](https://developer.apple.com/documentation/xcode/distributing-your-app-to-registered-devices) and Xcode 27.0 `xcodebuild -help`. The export exposes `CODE_SIGN_STYLE`, `DEVELOPMENT_TEAM`, `CODE_SIGN_IDENTITY`, and `PROVISIONING_PROFILE_SPECIFIER`: `Exports/iOS/Unity-iPhone.xcodeproj/project.pbxproj:1322`, `:1763`. Unity's `appleDeveloperTeamID`, `appleEnableAutomaticSigning`, `iOSManualProvisioningProfileID`, and `iOSManualProvisioningProfileType` are documented in the Editor's `UnityEditor.CoreModule.xml:41043` and `:41103`. `-allowProvisioningUpdates` can create or update assets for automatic signing and download profiles for manual signing; Xcode help names API key path, key ID and issuer ID options. A CI pipeline may choose explicit settings to avoid depending on whichever assets an agent happens to have, but that is an operational recommendation, not a platform requirement.
- Profiles have an `ExpirationDate`, and Apple says their lifetimes vary by type and are typically at most a year: [TN3125](https://developer.apple.com/documentation/technotes/tn3125-inside-code-signing-provisioning-profiles). Apple says code-signing certificates are typically valid for a year, varying by type: [TN3161](https://developer.apple.com/documentation/technotes/tn3161-inside-code-signing-certificates). Do not state a universal fixed lifetime. Personal Team installation profiles expire after seven days: Apple [account overview](https://developer.apple.com/help/account/basics/about-your-developer-account). Revoking a certificate invalidates profiles that contain it: Apple [Revoke a certificate](https://developer.apple.com/help/account/certificates/revoke-a-certificate).
- App Store distribution certificates can expire without stopping already distributed, Apple re-signed apps: confirmed by [TN3161](https://developer.apple.com/documentation/technotes/tn3161-inside-code-signing-certificates). Development, ad hoc and enterprise installed-app behavior should be described by their profile and membership rules, without transplanting the App Store rule. Apple [profile editing](https://developer.apple.com/help/account/provisioning-profiles/edit-download-or-delete-profiles) requires regeneration and re-signing after expiry; Apple [membership renewal](https://developer.apple.com/help/account/membership/renewal) has a separate 90-day enterprise membership grace period subject to valid certificates and profiles. A CI signing failure can follow expiry or revocation without a source change, but exact device behavior for every channel was not run.
- Apple's [TN3125](https://developer.apple.com/documentation/technotes/tn3125-inside-code-signing-provisioning-profiles) gives `security cms -D -i` for inspecting a profile. It warns that the familiar plist view is not the modern system's sole source of truth. No private provisioning profile was read in this phase.

### xcode-build-settings

- The export sets `IPHONEOS_DEPLOYMENT_TARGET = 15.0`: confirmed at `Exports/iOS/Unity-iPhone.xcodeproj/project.pbxproj:1331`; Unity's minimum supported iOS version is 15: [system requirements](https://docs.unity3d.com/6000.3/Documentation/Manual/system-requirements.html). A pod requiring a higher minimum can make installation or compilation fail; the outcome depends on the podspec and CocoaPods diagnostics, so do not invent a fixed message.
- `-ObjC` makes the linker load static-library members that implement Objective-C classes and categories: Apple [QA1490](https://developer.apple.com/library/archive/qa/qa1490/_index.html). The export explicitly sets it for `GameAssembly`: `Exports/iOS/Unity-iPhone.xcodeproj/project.pbxproj:1774`; the session's `xcodebuild -showBuildSettings` run found it on `UnityFramework` and `GameAssembly`, and not on `Unity-iPhone`. The project lists system and weak frameworks in `OTHER_LDFLAGS` for `UnityFramework`: `Exports/iOS/Unity-iPhone.xcodeproj/project.pbxproj:1945`.
- The export contains `SWIFT_VERSION = 5.0`, and no explicit `ALWAYS_EMBED_SWIFT_STANDARD_LIBRARIES` setting was found in its project file: `Exports/iOS/Unity-iPhone.xcodeproj/project.pbxproj:1347` and `:1961`. The former is a language setting, not evidence that Swift code is present or which runtime is embedded. Apple's [Swift 5 release notes](https://developer.apple.com/documentation/xcode-release-notes/swift-5-release-notes-for-xcode-10_2) say the Swift standard library is supplied for iOS 12.2 or newer variants. The session's `xcodebuild -showBuildSettings` run gave `ALWAYS_EMBED_SWIFT_STANDARD_LIBRARIES = NO` and `EMBEDDED_CONTENT_CONTAINS_SWIFT = NO` on all three code targets.
- Xcode 14 deprecated building with bitcode and stopped accepting bitcode submissions from Xcode 14: Apple [release notes](https://developer.apple.com/documentation/xcode-release-notes/xcode-14-release-notes). The export has `ENABLE_BITCODE = NO`: `Exports/iOS/Unity-iPhone.xcodeproj/project.pbxproj:1412`. A precise Unity version when the setting was removed was not verified and should be omitted.
- ATS requires HTTPS for HTTP through the URL Loading System, typically `URLSession`: Apple [NSAppTransportSecurity](https://developer.apple.com/documentation/bundleresources/information-property-list/nsapptransportsecurity). `NSAllowsArbitraryLoads` is a broad exception; `NSExceptionDomains` scopes named domains; `NSAllowsLocalNetworking` covers local names and IP addresses, with Apple documenting an iOS 17 change to IP-address defaults: Apple [NSAllowsLocalNetworking](https://developer.apple.com/documentation/bundleresources/information-property-list/nsapptransportsecurity/nsallowslocalnetworking). Native code using a lower-level stack is not automatically governed by `URLSession`'s ATS rule, so describe the actual client.
- Unity's [InsecureHttpOption](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/InsecureHttpOption.html) is explicitly about `UnityWebRequest`: `NotAllowed`, `DevelopmentOnly`, `AlwaysAllowed`. The iOS Player Settings default is Not allowed: Unity [iOS Player Settings](https://docs.unity3d.com/6000.3/Documentation/Manual/class-PlayerSettingsiOS.html). The default export has no `NSAppTransportSecurity` dictionary in `Exports/iOS/Info.plist`; the default Android export has no `usesCleartextTraffic` override in `Exports/Android-GameActivity/unityLibrary/src/main/AndroidManifest.xml`. Android itself disables cleartext for apps targeting API 28 or higher: Android [behavior changes](https://developer.android.com/about/versions/pie/android-9.0-changes-28). The outline's blanket Android-works/iOS-fails example is not supported for a default Unity project. Treat UnityWebRequest, native SDK code and web views as separate code paths. The session's exports then checked what each value of the setting writes into both projects (see Runs).
- `canOpenURL` requires queried schemes in `LSApplicationQueriesSchemes` and returns false for undeclared schemes; `openURL` does not need that list: Apple [UIApplication.canOpenURL](https://developer.apple.com/documentation/uikit/uiapplication/canopenurl(_:)). Apple currently documents a 50-entry limit for apps linked on or after iOS 15 and a 25-entry limit for apps linked on or after iOS 27. The export has one queried scheme from an earlier post-processor: `Exports/iOS/Info.plist:40`.
- `UIBackgroundModes` describes background services. Apple lists `audio`, `fetch`, `processing` and `remote-notification` and says Xcode populates the key from Background Modes capability selections: Apple [UIBackgroundModes](https://developer.apple.com/documentation/bundleresources/information-property-list/uibackgroundmodes) and [background execution](https://developer.apple.com/documentation/xcode/configuring-background-execution-modes). The default export has no `UIBackgroundModes` key in `Exports/iOS/Info.plist`; do not imply normal Unity background behavior automatically enables a background mode.
- A `PrivacyInfo.xcprivacy` manifest has keys for tracking, domains, collected data and required-reason API use: Apple [Privacy manifest files](https://developer.apple.com/documentation/bundleresources/privacy-manifest-files). Apple has rejected submissions missing covered API reasons since May 1, 2024: [required reason API](https://developer.apple.com/documentation/bundleresources/describing-use-of-required-reason-api). The same submission period imposed manifests and signatures for listed newly added SDKs: Apple [April 26, 2024 notice](https://developer.apple.com/news/?id=pvszzano) and [SDK requirements](https://developer.apple.com/support/third-party-SDK-requirements/). SDKs supply their own manifests; Xcode aggregates them into a privacy report: Apple [data use](https://developer.apple.com/documentation/bundleresources/describing-data-use-in-privacy-manifests). Apple says a missing reason produces an App Store Connect email before rejection under the stated policy.
- Unity 6000.3 ships `PlaybackEngines/iOSSupport/Tools/XCode/PrivacyInfo.xcprivacy` and the export places it in `UnityFramework`: `Exports/iOS/UnityFramework/PrivacyInfo.xcprivacy:4` and `Exports/iOS/Unity-iPhone.xcodeproj/project.pbxproj:450`. The exported manifest declares reasons for system boot time, disk space, user defaults and file timestamps. It is not an SDK manifest or a declaration of this app's collected data.

### xcode-cocoapods

- EDM4U's current [iOS Resolver documentation](https://github.com/googlesamples/unity-jar-resolver) describes `iosPods` and `iosPod` entries in dependency XML, Podfile generation and a `pod` post-build step. It offers integration into the Xcode project or the generated workspace, plus a setting to select that strategy. Its [changelog](https://github.com/googlesamples/unity-jar-resolver/blob/master/CHANGELOG.md) says that, since Unity 2019.3, pods are added to `UnityFramework` by default, and that static framework linkage is the default `use_frameworks!` mode. Inspect the exact installed EDM4U version and `target` or `addToAllTargets` declarations before saying a particular SDK links to the main target as well.
- A workspace-integrated CocoaPods project should be opened and built through the `.xcworkspace`: CocoaPods [Using CocoaPods](https://guides.cocoapods.org/using/using-cocoapods.html) and EDM4U [troubleshooting](https://github.com/googlesamples/unity-jar-resolver/blob/master/troubleshooting-faq.md). The bare export contains no Podfile, Pods project, or workspace. The session's run installed a local pod in a copy of the export: the `.xcodeproj` build failed linking `UnityFramework` with `ld: framework 'ProbePod' not found`, and the workspace build succeeded (see Runs).
- `Podfile.lock` records resolved versions; CocoaPods recommends keeping it under version control, and `pod install` honors locked versions while `pod update` selects newer versions: [Using CocoaPods](https://guides.cocoapods.org/using/using-cocoapods.html) and [install versus update](https://guides.cocoapods.org/using/pod-install-vs-update.html). `~> 0.1.2` means versions from 0.1.2 up to, but not including, 0.2: [Podfile syntax](https://guides.cocoapods.org/syntax/podfile.html). A lab needs a project with actual dependency declarations; the present probe has none.
- CI can use a Gemfile and Bundler to pin CocoaPods, plus the lockfile and a dependency cache: CocoaPods [Gemfile guide](https://guides.cocoapods.org/using/a-gemfile.html) and [CI guidance](https://guides.cocoapods.org/plugins/optimising-ci-times.html). Network or a prefilled cache is still needed for remote pod sources; the [Podfile syntax](https://guides.cocoapods.org/syntax/podfile.html) identifies the CDN as the default spec source. CocoaPods 1.16.2's `pod install --help` describes `--deployment` as disallowing any changes to the Podfile or the Podfile.lock during installation.
- Conflicting shared-pod version constraints are a resolver failure, not a last-one-wins choice: the installed Molinillo gem formats these as “could not find compatible versions”: `/opt/homebrew/lib/ruby/gems/3.4.0/gems/molinillo-0.8.0/lib/molinillo/errors.rb:106`. The lab should choose two compatible SDK dependencies and report the single resolved version from `Podfile.lock`. Two static libraries containing the same strong symbols can instead fail at link time with duplicate symbols; the session's run showed when (see Runs). Apple's [-ObjC note](https://developer.apple.com/library/archive/qa/qa1490/_index.html) explains why that flag can pull more object files from static archives.
- CocoaPods' [read-only plan](https://blog.cocoapods.org/CocoaPods-Specs-Repo/) is a dated proposal, posted 2024-11-30 and updated 2025-05, with a planned 2026-12-02 cutoff. On this chapter's 2026-09-25 evidence date, trunk had not yet reached that planned cutoff. Do not say it was already read-only.
- Swift Package Manager is supported: contradicted if the outline implies Unity or EDM4U cannot use it. The installed `UnityEditor.iOS.Extensions.Xcode.dll` exposes `PBXProject.AddRemotePackageReferenceAtVersion` and `AddRemotePackageFrameworkToProject`; the scratch C# harness compiled against it. EDM4U's [current documentation](https://github.com/googlesamples/unity-jar-resolver) says it parses `remoteSwiftPackage` XML and supports both Swift packages and CocoaPods. Its default Swift package target is `UnityFramework`, with an XML target selector for other targets.

## Rests on documentation alone

Signing identity, App ID and profile semantics; entitlement authorization; distribution-channel expiry effects; ATS and local-networking behavior; App Store Connect policy; privacy-manifest requirements; and the current CocoaPods and EDM4U workflows rest on the cited official documentation. The unsigned archive cannot test account-backed signing or an exported IPA. No profile from an account or keychain was inspected.

## Narrowed or cut

- Cut the blanket claim that an HTTP development server works on Android and fails on iOS. Defaults and client stacks vary, and the probe exports do not show an Android cleartext override or iOS ATS exception.
- Cut a fixed certificate or profile lifetime. Apple documents variation; a Personal Team has a separate seven-day rule.
- Cut a universal 50-scheme limit. Apple now documents 25 for apps linked on or after iOS 27.
- Cut a claim that every exported IPA includes dSYMs, or that none can include symbol-related content. No signed IPA was available to inspect, and `uploadSymbols` concerns App Store export behavior.
- Cut a precise Unity version when its bitcode control disappeared; it was not established here.
- Treat direct App Store Connect API upload as current but documentation-sensitive. Apple's newer build uploads resource and older Apps overview disagree.
- Left to a device: whether Unity's request code on Android consults Android's cleartext policy. No Android device or emulator was used, so the chapter says so.
- The chapter describes the IPA with Apple's words, as the distributed app that release builds keep small by leaving debug symbols in the dSYMs, and says nothing more about an IPA's contents.

## Where the outline fell short

The IL2CPP compile step is a `GameAssembly` shell phase, not a simple list of generated C++ source compilations in the main app target. Unity already exports a framework privacy manifest. EDM4U and Unity support Swift package references. Apple's current queried-scheme limits include iOS 27. CocoaPods trunk's read-only date was still a future plan at the evidence date. The lab cannot complete a signed export on a machine with no team or signing identity; it can archive unsigned and inspect that archive.

## Runs

The session ran these on 2026-09-25 with Unity 6000.3.11f1, Xcode 27.0 and CocoaPods 1.16.2, on a copy of the probe's `Exports/iOS` unless stated.

- Archive: `xcodebuild archive` of the `Unity-iPhone` scheme with `CODE_SIGNING_ALLOWED=NO` and no `-configuration`, so the scheme's Release, succeeded in 40 seconds. The archive held `Products/Applications/PlatformLayerProbe.app` (23 MB, unsigned per `codesign -dv`), `dSYMs/` with `PlatformLayerProbe.app.dSYM` and `UnityFramework.framework.dSYM` (123 MB), whose UUIDs matched their binaries under `dwarfdump --uuid`, `Signatures/` with a file for each of the two xcframeworks, and an `Info.plist` with empty `SigningIdentity` and `Team`. `UnityFramework.framework` carried Unity's `PrivacyInfo.xcprivacy`. The build's 56 warnings that libc++ no longer supports the platform all came from the `GameAssembly` phase, where IL2CPP's driver compiled with `-mios-version-min=11.0`, while the targets Xcode compiled used `arm64-apple-ios15.0`.
- Export: `xcodebuild -exportArchive` for `app-store-connect` and `debugging`, each with automatic and manual signing, stopped with `No Team Found in Archive`. With a made-up `teamID` in the options, it stopped at `No "iOS Distribution" signing certificate matching team ID "ABCDE12345" with a private key was found.` No IPA was produced, since no team or identity exists on this Mac. A fresh copy archived with `CODE_SIGNING_ALLOWED=NO` and `DEVELOPMENT_TEAM` set to that team still recorded an empty `Team`, and its export stopped at `No Team Found in Archive` again: an unsigned archive takes no team from the build setting, and `teamID` in the export options is what gets past the check.
- Settings: `xcodebuild -showBuildSettings -configuration Release` for the three code targets: deployment target 15.0, `dwarf-with-dsym`, `ENABLE_BITCODE = NO`, `SWIFT_VERSION = 5.0` and `ALWAYS_EMBED_SWIFT_STANDARD_LIBRARIES = NO` on each; `-ObjC` in `OTHER_LDFLAGS` for `UnityFramework` and `GameAssembly`; signing style Automatic on `UnityFramework` and `GameAssembly`, identity `iPhone Developer`, and no team.
